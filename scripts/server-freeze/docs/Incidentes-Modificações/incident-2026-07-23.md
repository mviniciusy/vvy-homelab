## Diagnóstico — Causa Raiz Confirmada

### EDAC (Error Detection and Correction) ativo

O servidor usa memória DDR3 ECC. O driver `edac_mc` + `edac_sbridge` (para chipset Sandy Bridge / Ivy Bridge) está ativo e reportando erros em tempo real.

### Evidências

```
EDAC MC0: 2 CE memory read error on CPU_SrcID#0_Ha#0_Chan#1_DIMM#0
  (channel:1 slot:0 page:0x667b98 offset:0x940 grain:32
   syndrome:0x0 - OVERFLOW area:DRAM err_code:0001:0091
   socket:0 ha:0 channel_mask:2 rank:0)
```

| Campo | Valor | Significado |
|---|---|---|
| `CE` | Correctable Error | Erro corrigido pela ECC — não derruba o sistema individualmente |
| `Chan#1_DIMM#0` | Canal 1, Slot 0 | Pente de 16GB (reposicionado) |
| `OVERFLOW` | — | Contador de erros estourou — MCE storm |
| `area:DRAM` | — | Erro no chip de DRAM em si |
| `err_code:0001:0091` | — | Erro de leitura na DRAM |

### State atual dos contadores EDAC

```
dimm3 (channel 1, slot 0): 16384 MB | CE=32
dimm9 (channel 3, slot 0): 8192 MB  | CE=0
```

- **Pente de 16GB (channel 1): 32 CE em 11 minutos** — ativo, erros continuam
- **Pente de 8GB (channel 3): 0 CE** — saudável

### Por que o servidor trava mas não desliga

> "Sempre que o servidor trava, ele não desliga, permanece ligado mas inacessível"

Isso é **hard lockup causado por MCE storm**. Quando os erros de ECC se acumulam muito rápido (`CE memory read error ... OVERFLOW`), o handler de MCE no kernel consome toda a CPU tentando logar, e eventualmente o processador trava. O watchdog de hardware não dispara porque a CPU está tecnicamente "rodando" (stuck no handler de MCE), não completamente congelada.

### Comparação com incidente anterior

O incidente de 22/Jul hipotetizou C-states do CPU como causa dos hard freezes. Agora sabemos que os freezes SEM mensagem no log eram causados por MCE storms que o kernel não conseguia logar a tempo (o handler travava antes de completar o log). Os boots -3 e -2 do incidente anterior (21/Jul) já mostravam MCE no Dimm6 — que era o pente de 16GB antes da troca de posição.

## Mudanças Aplicadas em 22-23/Jul

### 1. GRUB — 5 camadas de diagnóstico/captura

**Arquivo:** `/etc/default/grub`
**Backup:** `/etc/default/grub.bak.20260723`

#### Antes

```
GRUB_CMDLINE_LINUX_DEFAULT="quiet intel_iommu=on iommu=pt pcie_acs_override=downstream,multifunction video=efifb:off intel_idle.max_cstate=1 nmi_watchdog=0"
```

#### Depois

```
GRUB_CMDLINE_LINUX_DEFAULT="quiet intel_iommu=on iommu=pt pcie_acs_override=downstream,multifunction video=efifb:off intel_idle.max_cstate=1 nmi_watchdog=1 crashkernel=256M panic=10 hung_task_timeout_secs=60"
```

| Parâmetro | Função | Status |
|---|---|---|
| `nmi_watchdog=1` | Detecta hard lockups da CPU (IRQs desativadas) | Ativo após reboot |
| `crashkernel=256M` | Reserva 256MB para o kdump kernel capturar crash dump | Ativo após reboot |
| `panic=10` | Reboot em 10s se houver kernel panic (não fica travado) | Ativo (sysctl runtime) |
| `hung_task_timeout_secs=60` | Detecta tarefas travadas em 60s (era 120) | Ativo (sysctl runtime) |
| `intel_idle.max_cstate=1` | Limita C-states do CPU (mantido do incidente anterior) | Ativo |
