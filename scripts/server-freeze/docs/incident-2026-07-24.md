O servidor continuou travando após a mitigação `intel_idle.max_cstate=1`, indicando
que C-states do CPU não eram a causa única. A investigação se aprofundou em
kernel, drivers, e mismatch de versões de módulos.

## Incidente Específico — 24/Jul

### Sintoma

- Último alerta MCE/EDAC Monitor às 05:20 (CE=35, channel 1 slot 0 = Micron 16GB)
- Servidor travou por volta das 05:20 (13h31m de uptime desde boot -1)
- Journal do boot -1 termina abruptamente às 05:24 com entrada CRON normal
- Zero panic, zero OOM, zero kernel error no journal
- kdump ativo mas **nenhum crashdump gerado** — freeze foi hard demais
- Usuário reiniciou manualmente às ~11:55

### Pista — `panic_print` às 21:22

Única mensagem de kernel anômala no boot -1:

```
Jul 23 21:22:37 vvy kernel: Kernel: 'panic_print' sysctl interface will be obsoleted by both 'panic_sys_info' and 'panic_console_replay'
```

Apareceu 5h33m após o boot e 8h antes do freeze. Não é um panic — é um warning
sobre sysctl deprecated. Provavelmente não é a causa, mas indica que o kernel
estava lidando com algo incomum.

## Diagnóstico — Investigação Profunda

### Achado #1 — Kernel desatualizado (CRÍTICO)

| Item | Valor |
|------|-------|
| Kernel rodando | `6.17.13-6-pve` (30/Abr/2026) |
| Kernel mais recente instalado | `6.17.13-18-pve` (15/Jul/2026) |
| GRUB_DEFAULT | Pinado em `6.17.13-7-pve` (kernel inexistente) |
| Kernels instalados | 8 versões (-6, -9, -11, -13, -14, -15, -18, meta) |
| Todos os boots (-4 a 0) | Kernel `6.17.13-6-pve` |

O GRUB estava pinado em `6.17.13-7-pve` que não existe. O `update-grub` não foi
executado após as atualizações de kernel. O GRUB faz fallback para a primeira
entrada do submenu, que deveria ser `-18`, mas o pinamento em ID inexistente
fazia o servidor cair no kernel mais antigo (`-6`).

### Achado #2 — r8168 DKMS out-of-tree tainting kernel (ALTA)

- Driver `r8168` (Realtek proprietário) v8.055.00 instalado via DKMS
- Compilado **apenas** para o kernel `6.17.13-6-pve`
- Tainta o kernel: `out-of-tree module taints kernel` + `module verification failed: signature and/or required key missing`
- `r8169` (in-tree, mantido pelo kernel) cobre a RTL8111 (alias `pci:v000010ECd00008168sv*sd*bc*sc*i*`)
- `r8169` estava blacklistado por `/etc/modprobe.d/blacklist-r8169.conf`
- Aliases do r8168 em `/etc/modprobe.d/r8168-dkms.conf` faziam claim do PCI ID

### Achado #3 — Mismatch ZFS módulo vs userspace (descartado)

| Componente | Versão |
|-----------|--------|
| ZFS userspace tools | 2.4.3-pve1 |
| ZFS kernel module (kernel -6) | 2.4.1-pve1 |
| ZFS kernel module (kernel -18) | 2.4.2-pve1 |

Descartado como causa: **não há pools ZFS ativos**. Servidor usa LVM e diretórios.
Os módulos carregam mas não gerenciam I/O. Mismatch é irrelevante na prática.

### Achado #4 — Placa-mãe QIYIDA X79 genérica (MÉDIA)

- Fabricante chineso genérico, qualidade de VRM/capacitores incerta
- BIOS AMI 4.6.5 de Ago/2022 — pode ter bugs de ACPI/PM
- `intrusion1: ALARM` (chassis aberto ou sensor falhou)
- VRMs ficam quentes ao toque mas temps do CPU normais (38-43°C, crit 86°C)

### Achado #5 — NMI watchdog reativado (AGRAVANTE)

- GRUB cmdline tinha `nmi_watchdog=1` em vez do `nmi_watchdog=0` configurado
- Provavelmente revertido por um `apt upgrade` que rodou `update-grub` com
  config stale do `/etc/default/grub` antes da nossa correção
- NMI watchdog consome PMU counter permanentemente, causa latência

### Achado #6 — iTCO_wdt (hardware watchdog) não carregava (AGRAVANTE)

- Proxmox tem blacklist `blacklist iTCO_wdt` em `/lib/modprobe.d/blacklist_proxmox-kernel-*.conf`
- Override `install iTCO_wdt /sbin/modprobe --ignore-install iTCO_wdt` não funcionava
- `/sys/class/watchdog/` vazio — nenhum watchdog ativo
- Servidor travava e não reiniciava sozinho

### 4. Sysctls — forçar kdump em softlockup/hung_task/oops

**Arquivo:** `/etc/sysctl.d/99-panic-debug.conf`

```
kernel.softlockup_panic = 1
kernel.hung_task_panic = 1
kernel.panic_on_oops = 1
kernel.nmi_watchdog = 0
kernel.panic = 10
```

Se o freeze voltar a acontecer, o kernel agora vai:
1. Detectar soft lockup → panic
2. Detectar hung task (>60s) → panic
3. Detectar oops em módulo → panic
4. kdump captura crashdump com stack trace
5. Auto-reboot 10s após panic

### 5. rasdaemon — correlação MCE x freeze

- `apt-get install -y rasdaemon`
- `systemctl enable --now rasdaemon`
- Captura MCE com timestamp e endereço de página
- Permite correlacionar MCE no pente Micron com hard freezes

## Resolução — Boot com kernel 6.17.13-18-pve (24/Jul 13:00)

### Obstaculo: proxmox-boot-tool kernel pin

O `GRUB_DEFAULT` foi alterado para `0` e `update-grub` executado, mas o servidor
continuava bootando com o kernel `-6`. Apos tres tentativas falhadas (GRUB_DEFAULT=0,
GRUB_DEFAULT com ID textual, GRUB_DEFAULT=1>0, grub-install /dev/sda), descobriu-se
que o **`proxmox-boot-tool` tem seu proprio sistema de pinamento de kernel**
independente do GRUB:

```
$ proxmox-boot-tool kernel list
Pinned kernel:
6.17.13-6-pve
```

O pin foi removido com `proxmox-boot-tool kernel unpin`, que tambem rodou `update-grub`
automaticamente. Apos isso, o boot com kernel `6.17.13-18-pve` foi bem-sucedido.

### Obstaculo: iTCO_wdt blacklist em TODOS os kernels

Apos remover `blacklist iTCO_wdt` do arquivo
`/lib/modprobe.d/blacklist_proxmox-kernel-6.17.13-18-pve.conf` e regenerar o
initramfs, o modulo continuava deny-listed. Causa: o kmod lê **TODOS** os arquivos
de blacklist em `/lib/modprobe.d/`, incluindo os de kernels antigos (-6, -9, -11,
-13, -14, -15) que tambem continham `blacklist iTCO_wdt`. A solucao foi
remover as linhas `blacklist iTCO_wdt` e `blacklist iTCO_vendor_support` de
**TODOS** os arquivos de blacklist do Proxmox, nao so do kernel -18.

Apos isso, `modprobe iTCO_wdt` funcionou e o hardware watchdog carregou:
```
$ cat /sys/class/watchdog/watchdog0/identity
iTCO_wdt
```
