### Lições

1. **Pitfall HaGeZi — formato importa**: A HaGeZi distribui em vários
   formatos. Para Pi-hole, `dnsmasq/pro.txt` **não funciona** — usa sintaxe
   `local=/domain/` que o Pi-hole ignora (0 domínios parseados). O caminho
   **correto** é `adblock/pro.txt` (formato Adblock Plus), suportado pelo
   Pi-hole v6 como "ABP-style domains". Sempre validar com `pihole -g` e
   checar "Parsed N exact domains and M ABP-style domains" — se ambos
   forem 0, o formato está errado.

2. **`pct exec` não expõe `/usr/local/bin`**: o binário `pihole` retorna
   "No such file or directory" via `pct exec 101 -- pihole ...`. Usar
   sempre caminho absoluto: `pct exec 101 -- /usr/local/bin/pihole ...`.

3. **`pihole -up` é all-or-nothing**: sobe Core+Web+FTL juntos. Não há
   flag `--check` que execute de verdade (só sai antes de fazer). Se você
   quisesse atualizar só o FTL, teria que usar `pihole checkout ftl v6.7`.

4. **Adicionar lista vs adicionar bloqueador**: a pergunta original do
   usuário foi "tem como instalar outro bloqueador junto a ele? isso
   criaria latência ou perda de rede?". Resposta: não precisa — Pi-hole é
   DNS central e adicionar mais listas à gravity existente é o caminho
   correto. Um segundo bloqueador DNS (AdGuard Home, NextDNS) em paralelo
   não faria sentido (clientes teriam que ser configurados pra consultá-lo
   manualmente). O custo de mais listas é mínimo: FTL saltou de 167→180MB
   de RAM. updateGravity é atômico (recompila em paralelo, swap no final,
   DNS para <1s).
